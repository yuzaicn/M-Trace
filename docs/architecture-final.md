# M-Trace 工程方案定稿（阶段 2）

**版本** v1.0 · **日期** 2026-09-15 · **对应 issue** GUCH-363（父：GUCH-353）
**接口契约** 见同目录 `docs/interface.md`（v1.0-frozen）；**机器可读类型** 见 `src/types/`

本文回答三个问题：**为什么这么设计**、**每个模块怎么写**、**怎么算做完了**。
接口签名不在本文重复，以 `docs/interface.md` 为准。

---

## 1. 设计出发点（三条，其余都是推论）

### 1.1 这个产品的核心缺陷不是"认不出"，是"认错还嘴硬"

分析报告的实测结论里，只有一条能把项目做死：**13 个库外模型 36/36 全部被硬归因**，平均置信度 0.748，且与库内正确样本的置信度分布**重叠、阈值分不开**。

"阈值分不开"是关键信息 —— 它意味着**这个缺陷不能靠调参解决**，调高阈值只会同时砍掉库内正确率。所以它必须在**架构层**解决：把"这是不是一次模型采样"和"这是哪个模型"拆成两段独立的判断。前者不需要参考库，因此对库外模型同样有效；后者在距离门槛外一律弃权。

这条推论产出契约里的两段式决策，也是本项目与"随便算个相似度排行榜"的分界线。

### 1.2 零依赖不是洁癖，是产品论点

一个"判断模型真伪"的工具，如果自身带着几十个传递依赖，它的可信度叙事就自相矛盾 —— 上游任何一个包被投毒，都会直接变成错误的归因结论。分析报告用一次真实挫折证明了代价可控：在无法 `pip install numpy` 的环境里，作者用纯 Python 手写 Jacobi 特征分解完成了全部实验，并达到与参考实现 467/468 的一致率。

同样的算法在 TypeScript 里约 300 行。所以 ADR-001（`dependencies: {}`）不是"能省则省"，而是**把可审计性作为产品能力的一部分**。

### 1.3 报告的结论必须能被陌生人推翻

产品要说服的对象是"怀疑自己买了掺假渠道的开发者"。他们最合理的反应是"凭什么信你"。唯一站得住脚的回答是：**给你证据包和库文件，你自己跑一遍，得到逐字节相同的结论；如果不同，就是我们错了。**

这条要求反向约束了几乎所有设计：结论里不能有时间戳（否则两次运行字节不同）、随机源必须注入（否则不可复现）、库必须有内容哈希（否则"同一个版本号"可能指两份不同的数据）、序列化必须规范（否则哈希不稳定）。

## 2. 架构总览

```
                 ┌──────────────────────────────────────────┐
                 │              src/types/                   │  契约类型，无逻辑
                 └──────────────────────────────────────────┘
                                    ▲  (单向依赖，禁止反向)
   ┌────────────┬──────────────┬────┴───────┬──────────────┬────────────┐
   │            │              │            │              │            │
 config/      probe/       normalize/   stats/       fingerprint/  library/
 读本机配置    唯一触网面     → 观测      纯数学       → 特征向量    库校验/索引
   │            │              │            │              │            │
   └────────────┴──────────────┴────────────┴──────┬───────┴────────────┘
                                                   ▼
                                          ┌─────────────────┐
                                          │  credibility/   │  第一段：是不是采样？
                                          └────────┬────────┘
                                                   ▼
                                          ┌─────────────────┐
                                          │   attribute/    │  第二段：top-N + 拒判
                                          └────────┬────────┘
                                                   ▼
                              ┌──────────────┬─────┴──────┬─────────────┐
                              │              │            │             │
                          evidence/      report/       i18n/         cli/
                          证据包        HTML 渲染     文案目录      编排/退出码
```

**数据流的三个关键性质**：

1. **触网只发生在 `probe/`**，因此"测试不触网"是一个可检验的性质，而不是承诺。
2. **从 `normalize/` 往后全是纯函数**，因此同一份证据在任何机器上跑出同一结论。
3. **`credibility/` 与 `attribute/` 串联而非并联** —— 第一段否定时第二段根本不执行。

## 3. 逐模块实现要点

### 3.1 `src/config/` —— 本机配置发现

**要实现的**：按固定优先级合并 CLI 参数 / `MT_*` / `OPENAI_*`·`ANTHROPIC_*` / `~/.codex/config.toml`，输出 `ConfigSummary`。

**必须处理的失败路径**：

| 场景                          | 行为                                                            |
| ----------------------------- | --------------------------------------------------------------- |
| 无任何配置来源                | `CONFIG_NOT_FOUND`，退出 2；**不崩溃**，提示手动模式与 `--help` |
| 配置存在但解析失败            | `CONFIG_MALFORMED`，报出**具体字段名**（P0-1 ④）                |
| 多来源同一字段冲突            | 取高优先级 + 写一条 `source-conflict` 警告                      |
| 端点字符串无法解析            | `CONFIG_INCOMPLETE`；不猜测                                     |
| 被要求读 `auth.json` 的字段值 | `CONFIG_READ_FORBIDDEN`，直接拒绝                               |

**最容易写错的地方**：`auth.json` 只允许 `fsPort.exists()`。实现期最自然的写法是"顺手读出来看看有没有 key"，这一步就把凭据读进了内存，随后可能进日志。契约测试会扫源码断言 `auth.json` 不出现在任何读取调用的实参位置。

**最小可验收用例**：构造函数化的 `fsPort` 桩（`exists` 返回 true、`readTextFile` 记调用），跑 `discoverConfig`，断言 `readTextFile` **从未被调用**。

---

### 3.2 `src/probe/` —— 挑战套件与传输

**要实现的**：`TransportPort` 的 HTTP/SSE 实现 + 重试/退避/限流/中止 + 挑战套件渲染。

**必须处理的失败路径**：E01–E05、E13（见 `docs/interface.md` §4）。

**最容易写错的地方**：

1. **把超时当致命错误**。第一次超时就整体失败，会让一次 90% 成功的检测归零。契约要求逐条记 `failures` 并继续。
2. **429 后立刻重试**。必须尊重 `Retry-After` 并把并发降到 1 —— 否则会把用户的账号推进风控（法务 R10/R11 的落点）。
3. **header 全量哈希**。网关的 `x-request-id` 每次不同，全量哈希会把它变成纯噪声。只读白名单。
4. **`stream: true` 被忽略时判失败**。那是降级不是失败（E03）。

**最小可验收用例**：起一个绑定 `127.0.0.1:0` 的真实 HTTP server，用一个 `scenario` 查询参数切换行为（正常 SSE / 429 带 Retry-After / 中途断开 / 空体），断言四条路径各自的 `MError.code` 与重试次数。**必须是真实 server，不是函数桩** —— 只有真实 socket 才能覆盖分块边界与连接中断。

---

### 3.3 `src/normalize/` —— 容错解析与改写记账

**要实现的**：从 `rawText` 中提取值序列，剥 markdown 围栏，提取首个合法 JSON，并记录所有异常。

**契约要点**：解析失败必须是 `values: null`。**这一条比看上去重要**：如果失败返回 `[]`，下游的分箱会得到一个空计数向量，与"合法但全零"无法区分，最终表现为"这个模型的分布很奇怪"而不是"这条样本坏了"。

**最容易写错的地方**：把"抠不出数字"和"输出被改写"合并成一种情况。契约区分 `parseFailure`（这一条为什么坏）与 `flags`（这一条经历了什么）。改写比例是**降级决策的输入**（> 30% → 整轮 `unknown`），合并后就算不出来了。

**最小可验收用例**：五份固定输入（裸 JSON / ```json 围栏 / 前后带解释文字 / 被改写成自然语言 / 只有空白），断言各自的 `parseFailure`、`flags` 与 `values`。

---

### 3.4 `src/stats/` —— 统计核心

**要实现的**：`docs/interface.md` §3.4 列出的全部函数面，自实现，零依赖。

**最容易写错的地方**：这类 bug **不会崩，只会让结论悄悄偏**。`regularizedGammaP` 的级数/连分数切换点写错，χ² 的 p 值就在某些区间系统性偏大，表现是"某些模型的置信度略高"—— 没人会注意到。

因此对照基准（SciPy / R 生成的固定期望值，以 JSON 夹具提交）是**永久门禁**，不是一次性检查。夹具提交进仓库，因此 CI/本机都不需要装 Python。

**最小可验收用例**：对固定输入断言 Hellinger / χ² 上尾 / 自相关的期望值在 1e-9 相对误差内。

---

### 3.5 `src/credibility/` —— 第一段决策

**要实现的**：`assessCredibility(values, policy, rng)` → `CredibilityAssessment`。

四个信号：`chi-square-over-df`（真实采样中位 0.332）、`lag1-autocorrelation`（中位 −0.587）、`distinct-ratio`（中位 0.953）、`repeat-rate`（中位 0.047）。

**契约要点**：判据区间**全部来自库**（`policy.ranges`）。代码里出现 `0.332` 这类数字就是违约 —— 那是校准数据，改动它必须伴随重新校准与留证。

**最容易写错的地方**：

1. **用样本量不足的序列硬算自相关**。n < 30 时 lag-1 自相关的方差极大。样本不足时应让该信号"不参与判断"，而不是给出一个噪声值。
2. **把 `implausible` 当成错误**。它是**结论**：`unknown` + `abstention: 'implausible-as-sampling'`，报告照常生成，退出码 10 而不是 4。

**最小可验收用例**：三份合成序列 —— ① 带重复惩罚的采样模拟（应 `plausible`）；② iid 均匀（应 `implausible`）；③ 全常数（应 `implausible`）。三者都必须走到 `unknown` 而不是硬归因。

---

### 3.6 `src/fingerprint/` —— 特征提取

**要实现的**：观测 → `Fingerprint`（按族组织 + 传输特征 + 质量评级）。

**契约要点**：族与特征**可缺席**。缺席表示"不可计算"，不是 0。用 0 填充会让"传输族整族失效"变成一个看起来正常的特征向量，最终污染距离计算。

**最容易写错的地方**：把 `quality.grade` 算成一个装饰性字段。它是**短路条件**：`poor` 一律不进归因。

**最小可验收用例**：给定一份全部非流式的观测，断言流式节奏类特征**整键缺席**（不是 0）、`quality.grade = 'poor'`、`degradedReasons` 含对应键。

---

### 3.7 `src/library/` —— 参考库

**要实现的**：结构校验、哈希重算、门限重算、索引。

**契约要点**：

- 三段版本不兼容 → **拒绝加载**，不静默降级
- `integrity.contentHash` 重算不符 → `LIBRARY_MALFORMED`
- 条目的可用性由加载器**按门槛重算**，不采信文件里的 `usable`

**最容易写错的地方**：把哈希不符做成警告。那样"库被改过"就只是一个控制台提示，而报告照样给出结论。契约要求它是硬失败 —— 一个能自证被篡改的库，比一个能给答案的库重要。

**最小可验收用例**：① 改一个字节 → 加载失败；② 改 `extractorVersion` → `LIBRARY_VERSION_UNSUPPORTED`；③ 样本量不足的条目 → 进 `excluded` 且不出现在候选中。

---

### 3.8 `src/attribute/` —— 第二段决策

**要实现的**：`docs/interface.md` §2.2 的七步规则。

**最常见写错的地方，按危险程度排序**：

1. **省掉第 4 步**（距离上限）。这是最诱人的简化："反正用户想知道最像的是谁"。省掉它，库外模型 100% 被硬归因 —— 也就是回到本项目的起点缺陷。
2. **confidence 用 softmax 归一化**。softmax 的分母只涉及库内候选，库外模型也会有接近 1 的置信度（分析实测均值 0.748 正是这么来的）。置信度必须由**绝对量**（距离、边际、有效样本比）驱动。
3. **`ambiguous` 缺失**。只有"命中/未命中"两档时，两个同样接近的候选会被任意选一个，而正确答案是"分不开，多跑几个变体"。
4. **`reasons` 留空**。报告要靠它解释"为什么拒判"；空数组会让报告只能显示"无法判定"四个字。

**最小可验收用例**：用 `docs/interface.md` §2.2 的七步各构造一份输入，断言 `decision` / `stage` / `abstention` 三元组；并断言同一输入两次调用输出**逐字节相同**。

---

### 3.9 `src/evidence/` —— 复验载体

**要实现的**：`canonicalJson`（已交付）、序列化/反序列化/摘要。

**最容易写错的地方**：`canonicalJson` 的实现差异。它是复验契约的底层原语 —— 键序、`-0`、非 ASCII、`undefined` 处理任何一处不同，第三方复算的哈希就不一致，而失败表现是"对方说我们算错了"，极难排查。已交付的实现在 `src/core/canonical.ts`，并有 11 条冻结字节的测试。

**最小可验收用例**：同一逻辑值用不同键序构造，断言哈希相同；含 `-0` / 非 ASCII / 可选字段的对象，断言哈希稳定。

---

### 3.10 `src/report/` —— 视图模型与渲染

**要实现的**：`buildReportViewModel`（脱敏 + 格式化 + 裁剪）与 `renderReport`（纯 HTML 字符串）。

**契约要点**：

- 单文件、CSS 内联、数据内联、**零执行脚本**、零外部 URL
- 交互全靠纯 CSS（`<details>` / `:target` / checkbox hack）
- 体积上限 2 MiB，超限裁剪附录并**明写**

**为什么坚持无脚本**：报告里会出现从第三方端点采回的文本。如果用 JS 动态渲染，就引入了注入面；纯 CSS + 转义彻底消除这一整类问题，安全评审会显著变短。代价是图表不能缩放 —— 用静态 SVG + 数值表替代。

**最容易写错的地方**：

1. **脱敏放在渲染层**。必须在 VM 阶段完成，渲染层不信任上游。
2. **裁剪时静默**。用户必须看到"附录已裁剪"，否则会以为拿到了全部证据。
3. **`limitations` / `disclaimerKeys` 留空**。这是产品 P0-7 与法务 R13 的硬要求。

**最小可验收用例**：渲染一份固定 VM，断言 ① 无 `<script>` 执行块、② 无 `http(s)://` 外部引用、③ 凭据正则扫描零命中（含正反例）、④ 两种 locale 都完整。

---

### 3.11 `src/i18n/` 与 `src/cli/`

**i18n**：目录按相对入口文件加载；缺键返回 `⟦missing:<key>⟧` 而不是抛错（快照测试据此抓漏翻）。

**cli**：参数解析 → 编排 → 返回退出码（**不调用 `process.exit`**）。已交付的骨架在 `src/cli/entry.ts`，覆盖 `--help` / `--version` / 未知 flag 三条路径；阶段 3 接入真实管线。

## 4. 工程配置（本 issue 已落地）

| 文件                  | 作用                                                                                                                                                                               |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tsconfig.json`       | 严格模式基线。`strict` + `noUncheckedIndexedAccess` + `exactOptionalPropertyTypes` + `erasableSyntaxOnly`。最后一条禁止 `enum`/`namespace`，使源码可被 Node 的原生类型擦除直接运行 |

**夹具回归的三条硬规则**（写在夹具里而不是代码里）：

1. **零误归因**：`expected.decision` 为 `unknown` 的用例被判 `in-library` → 门禁失败，**无论总体准确率多高**。
2. **稳定性**：同一条夹具重复运行必须得到逐字节相同的候选与置信度。
3. **阈值不在代码里**：判定所用阈值必须来自库文件的 `calibration`。
